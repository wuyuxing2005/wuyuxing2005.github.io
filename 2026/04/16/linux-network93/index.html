(93) timerfd驱动的定时器队列与当前实现里的几个坑

发表于2026-04-16|更新于2026-04-16|linux_network
|浏览量:

这篇文章记录一下我现在写到的 timer 模块。

这部分代码的目标很明确：不给每个定时任务单独开线程，而是把所有定时器统一交给 EventLoop 管理。这样定时器触发就能和网络事件一样，统一落到 reactor 的事件循环里处理。

为什么这里要用 timerfd

前面网络部分已经有了 epoll + EventLoop + Channel 这一套事件分发框架。

如果定时器仍然用 sleep、轮询或者额外线程来做，就会和现有模型割裂开。相比之下，timerfd 的好处是它本质上就是一个文件描述符，可以直接被 epoll 监听。

也就是说，网络连接可读是一个事件，定时器到期同样也可以表现成一个“可读事件”。

这样做有几个直接好处：

  • 定时器和 I/O 事件统一进入 EventLoop
  • 不需要为每个定时任务创建线程
  • 触发逻辑更清晰，回调函数可以直接复用现有的事件分发思路

当前几个类的职责

我现在这部分代码里主要有三个核心对象。

1. TimeStamp

TimeStamp 是对时间戳的简单封装，内部保存微秒级时间。

它的作用主要有两个：

  • 表示某个定时器的到期时间
  • 让定时器可以按时间先后进行比较和排序

因为后面 TimeQueue 里需要把定时器放到有序容器中，所以 TimeStamp 的比较操作是必须的。

2. Timer

Timer 表示单个定时任务，核心信息包括：

  • expiration：下一次到期时间
  • interval：如果是重复定时器，那么它的周期是多少
  • CallBack：到期后真正要执行的逻辑
  • isRepeat：是否重复触发

所以 Timer 本质上就是“什么时候执行 + 执行什么 + 要不要重复”这三件事的封装。

3. TimeQueue

TimeQueue 才是这部分代码的核心。

它做了几件关键的事：

  • 创建 timerfd
  • 给 timerfd 绑定一个 channel
  • 把 channel 注册进 EventLoop
  • 用 std::set<std::pair<TimeStamp, Timer *>> 维护全部定时器
  • 当 timerfd 可读时，找出所有已经到期的任务并执行回调

这实际上就是一个“小型定时器调度器”。

我现在对这一部分的整体理解

写完这一版之后，我对定时器模块的理解基本可以概括成一句话：

timerfd 负责把“时间到了”这件事转换成一个文件描述符事件，TimeQueue 负责维护所有定时任务的顺序，Timer 负责保存单个任务的回调和周期信息。

也就是说：

  • timerfd 解决“怎么通知”
  • set 解决“谁最先到期”
  • Timer 解决“到期之后做什么”

这个设计和前面的 epoll + channel + EventLoop 是一致的，所以把 timer 模块接进整个网络库是很自然的。

下一步准备做什么

我准备接下来优先修这几件事：

  1. 把 ReadFd() 改成标准的 read(timerfd, &howmany, sizeof(howmany))
  2. 把 ResetTimers() 的遍历对象改成 active_timers
  3. 在重排完定时器后重新设置 timerfd
  4. 统一 interval 和 TimeStamp 的时间单位

如果这些问题修顺了，这个 timer 模块就基本能稳定承担连接超时、定时关闭、周期任务之类的功能了。
