(94) close流程、to_do_list延迟清理与Connection析构时机

发表于2026-04-17|更新于2026-04-17|linux_network
|浏览量:

这篇文章记录一下我现在对连接关闭这部分代码的理解。

前面把 Connection、channel、EventLoop、Server 这一套跑通之后，我一开始对 close0() 也有一个很自然的误解：名字叫 close，那它是不是调用之后就立刻把 fd 关掉了？

但顺着代码看完之后会发现，这里实际上分成两层：

  • 一层是逻辑上的关闭，也就是告诉服务器“这个连接不要再用了”
  • 一层是真正的资源释放，也就是把 channel 从 epoll 里摘掉，并在最后调用 ::close(fd)

这两层没有放在同一个时刻做，原因正是为了避免事件回调执行到一半时对象被提前析构。

先说结论：close0 不是立刻 close(fd)

当前实现里：

Connection::close0() 做的事情非常克制，它并不直接调用 ::close(fd)，而是通过回调把删除连接这件事交给 Server::deleteConnection()。

也就是说，close0() 的语义更接近：

  • 这个连接应该被回收了
  • 请 Server 把它从连接管理结构里移除
  • 具体的销毁动作不要在当前回调栈里立刻做

这一点非常关键，因为 Connection 当前很可能还处在它自己的事件回调流程中。

第六步：shared_ptr 计数归零，Connection 才真正析构

在 Server::deleteConnection() 里，connections.erase(it) 只是去掉了服务器哈希表中的那一份引用。

但当前对象通常还至少有几份引用：

  • 当前事件处理过程中 channel::Tie() 机制保住的一份临时引用
  • to_do_list_ 中绑定 con 时额外保存的一份引用
  • Server::deleteConnection() 里的局部变量 con

因此 Connection 不会在 erase() 的瞬间就消失。

只有当：

  • 当前回调执行结束
  • DoToDolist() 执行完成
  • 这些临时 shared_ptr 都依次释放

最后引用计数归零时，Connection 才会真正进入析构。

为什么一定要有 to_do_list_

这部分是我觉得最容易想岔的地方。

如果没有 to_do_list_，最直接的写法就是：

  • close0()
  • Server::deleteConnection()
  • 立刻把 Connection 析构掉

但这样做有一个非常危险的问题：

当前这个连接所属的 channel 很可能还在执行：

而 handleEventByCallBack() 里面会继续调用这个连接的读写回调。也就是说，此时回调栈上仍然在使用 Connection 里的成员，比如：

  • this
  • ch
  • readBuffer
  • sendBuffer
  • mysc

如果在回调中途把 Connection 提前析构，那么这些成员都会变成悬空对象，后面继续执行就是典型的野指针/空悬引用问题。

所以 to_do_list_ 的核心价值不是“做个延迟队列”，而是：

  • 把析构时机推迟到当前这一轮事件处理完成之后
  • 保证不会在 channel 正在执行自己的回调时，把其所属的 Connection 提前释放

这其实是一种很典型的 reactor 场景下的延迟销毁策略。

当前这套析构流程为什么是合理的

现在回头看，这一整套流程其实是在刻意把“关闭连接”拆成几个独立步骤：

1. 业务层面不再使用这个连接

也就是从 connections 哈希表中移除。

2. 事件层面不再监听这个连接

也就是把 channel 从 epoll 中摘掉。

3. 对象生命周期自然结束

也就是等 shared_ptr 计数归零后再析构 Connection。

4. 最后释放底层 fd

也就是在 mysocket::~mysocket() 中调用 close(fd)。

这种拆法的好处在于，每一步的语义都更清晰：

  • 先停止管理
  • 再解除事件监听
  • 最后释放资源

而不是把所有动作粗暴地塞进一个“close”动作里一次做完。

这一部分我现在的整体理解

所以现在如果让我用一句话总结这部分设计，我会这样表述：

当前实现中的 close0() 只是关闭流程的起点，它负责通知 Server 回收连接；to_do_list_ 负责把回收时机推迟到本轮事件处理结束之后；tie_ 负责保证当前回调执行期间对象仍然存活；最后真正的 ::close(fd) 发生在 Connection 持有的 mysocket 析构时。

把这几层分开理解之后，这段代码就会清楚很多。

之前我看到 close0() 时，总会下意识觉得“关闭连接”应该一步到位。现在看下来，在 reactor 模型里，真正安全的做法恰恰不是一步到位，而是把销毁动作拆开并延后。

这也是这部分代码最值得记下来的一点。
